# Modeling Conventions

> The rules every table in this model obeys, and the places where it deliberately does not. Read this
> before adding a table; the per-domain files assume it.

**Version:** v0.2 · **Last updated:** 2026-09-10 · **Applies to:** all 10 domains in [`domains/`](domains/)

---

## 1. Naming

```sql
-- Tables:        snake_case, plural                  → users, sign_localizations, ai_models
-- Columns:       snake_case, descriptive             → failed_login_attempts, consent_granted_at
-- Primary key:   [singular_table]_id                 → user_id, sign_id, notification_type_id
-- Foreign key:   [referenced_table_singular]_id      → category_id, translation_id
-- Indexes:       idx_[table]_[purpose]               → idx_users_status, idx_lexicon_lang_type
-- Unique index:  uq_[what_is_unique]                 → uq_provider_identity, uq_sign_localization
-- Check:         ck_[table]_[rule]                   → ck_push_requires_device
-- Enum types:    snake_case, singular                → user_status, notification_channel
-- Enum values:   UPPER_SNAKE_CASE                    → PENDING_VERIFICATION, MODEL_INFERENCE_ERROR
```

**The primary key is not called `id`.** `user_id` stays `user_id` in every table that references it, so
a join never renames anything and `USING (user_id)` always works. This is a deliberate departure from
the scaffold's `id` convention, and it is the more useful one in a schema with 28 foreign keys.

**A table with no foreign key still belongs to a schema.** `identity.password_policies` references
nothing and is referenced by nothing — it is placed by **who reads it**, not by what it joins to. Schema
membership is an ownership statement, not a graph property.

**`position` is a column name in `multimedia_resources` and `translation_signs`.** PostgreSQL classifies
`POSITION` as non-reserved, so it works unquoted — but ORMs and some tooling quote it inconsistently.
Keep it; do not introduce more columns whose names collide with SQL functions.

## 2. Keys

| Rule | Reason |
|------|--------|
| **UUID v4, generated by the database** (`gen_random_uuid()`) | Ids must be generatable on the client for offline queueing and must not leak volume. A sequential id tells anyone how many users the system has |
| **No surrogate key on pure junction tables** | `user_roles` and `role_permissions` use the composite of their two foreign keys as the primary key. A third id would add nothing and would allow the same pair twice |
| **Composite primary keys on aggregate tables** | `usage_daily_stats` is keyed by `(stat_date, section, event_type)`: the grain *is* the key |

## 3. Timestamps

Always `TIMESTAMPTZ`, never `TIMESTAMP`. The application serves one timezone today (`America/Bogota`)
and that is exactly why: a model that stores local time is correct until the first day someone runs a
report from another timezone, and then it is silently wrong forever.

`usage_daily_stats.stat_date` and `users.birth_date` are `DATE`, deliberately — a calendar day in
Colombia and a date of birth are not instants.

## 4. Audit columns and soft delete — where this model deviates

The scaffold prescribes `created_at`, `updated_at`, `deleted_at`, `created_by`, `updated_by` on every
table. **This model does not do that, and the deviation is the correct one.**

| Column | Where it actually appears | Why not everywhere |
|--------|---------------------------|--------------------|
| `created_at` | Almost every table | Insert-only tables name it after the fact instead: `error_logs.occurred_at` |
| `updated_at` | Only tables updated in place: `users`, `user_preferences`, `sign_lexicon`, `sign_localizations`, `user_achievements`, `password_policies` | An `updated_at` on an append-only log is a column always equal to `created_at`. It is noise |
| `deleted_at` | Only `users` and `translations` | The only two entities the *user* can delete (RNF8 and ERF5.5). Everything else is retired by status (`content_status`, `is_active`, `revoked_at`) or is a log that is never deleted |
| `created_by` / `updated_by` | Only `sign_lexicon` | Only catalog content has an editorial author worth recording. Who created a notification is the system |

**Soft delete is applied where deletion is a user right, not as a blanket policy.** Blanket soft delete
on 29 tables means 29 `WHERE deleted_at IS NULL` clauses that someone will eventually forget, and the
row that leaks is the one that was supposed to be gone. Retirement by status is stronger where it fits:
a sign with `status = 'INACTIVE'` is invisible to end users *and* still joinable from
`translation_signs`, which is exactly what a history that must not break needs.

**`updated_at` does not update itself.** `DEFAULT CURRENT_TIMESTAMP` fires on insert only. Without a
trigger the column is a creation timestamp with a misleading name — the trigger is in
[`constraints.md`](constraints.md), and its absence is DATA-07.

## 5. Referential actions, and what each one means

The model uses all three, and the choice per relationship carries meaning:

| Action | Used for | Reading |
|--------|----------|---------|
| `ON DELETE CASCADE` | Rows that are part of the user: auth providers, tokens, preferences, devices, translations, achievements | "This has no existence without its owner" |
| `ON DELETE SET NULL` | `usage_events.user_id`, `audit_logs.user_id`, `error_logs.user_id`, `user_sessions.user_id` | "The fact survives the person." A deleted account must not erase the statistics or the audit trail — a trace that disappears with the account is not a trace |
| `ON DELETE RESTRICT` | `user_roles.role_id`, `sign_lexicon.category_id`, `translation_signs.sign_id`, `translations.model_id`, `ai_models.trained_by` | "This is referenced by history; deleting it would rewrite the past" |

> **The clearest illustration is a pair of opposites.** `translations.user_id` is `CASCADE` and
> `usage_events.user_id` is `SET NULL`. Same deletion, opposite answers, both correct: the translation
> history is the user's personal data (RNF8), and a usage event is an anonymous statistical fact (RF6).

## 6. Polymorphic references

Three places name a record in another domain **without a foreign key**:
`notifications.reference_type`/`reference_id`, `usage_events.reference_type`/`reference_id`, and
`audit_logs.entity_type`/`entity_id`.

This is deliberate in all three, for the same reason: the referenced table is not known at schema time,
and in the Notifications case a real foreign key would make it depend on Gamification, which may never
exist. **The price is that the database cannot check the reference and the application must.** Every
such pair gets a composite index so the reverse lookup stays a query rather than a scan.

Do not add a fourth without the same justification.

## 7. Enum catalog

Twenty-one enum types. Every one exists to stop a typo from becoming silently corrupt data — a
`VARCHAR` status column is a column that will eventually hold `'Active'`, `'ACTIVE '` and `'activo'`.

```sql
-- Identity
CREATE TYPE user_status          AS ENUM ('ACTIVE', 'INACTIVE', 'BLOCKED');
CREATE TYPE auth_provider        AS ENUM ('GOOGLE', 'FACEBOOK');
CREATE TYPE session_status       AS ENUM ('ACTIVE', 'CLOSED', 'EXPIRED');
CREATE TYPE token_type           AS ENUM ('EMAIL_VERIFICATION', 'PASSWORD_RESET');

-- Lexicon
CREATE TYPE content_status       AS ENUM ('ACTIVE', 'INACTIVE', 'DRAFT');
CREATE TYPE sign_type            AS ENUM ('LETTER', 'WORD', 'PHRASE');
CREATE TYPE resource_type        AS ENUM ('IMAGE', 'VIDEO', 'ANIMATION');
CREATE TYPE sign_language        AS ENUM ('LSC');                    -- ISO 639-3: 'csn'
CREATE TYPE ui_language          AS ENUM ('ES', 'EN');               -- i18n: 'es', 'en'

-- Translation and AI
CREATE TYPE output_mode          AS ENUM ('TEXT', 'AUDIO');
CREATE TYPE sample_type          AS ENUM ('VIDEO', 'LANDMARKS', 'IMAGE');

-- Notification
CREATE TYPE device_platform      AS ENUM ('ANDROID', 'IOS', 'WEB');
CREATE TYPE notification_channel AS ENUM ('PUSH', 'EMAIL', 'IN_APP');
CREATE TYPE notification_status  AS ENUM ('PENDING', 'SENT', 'FAILED', 'READ', 'CANCELLED');

-- Usage
CREATE TYPE usage_section        AS ENUM ('HOME', 'TRANSLATION', 'ALPHABET', 'LEXICON', 'HISTORY',
                                          'PROFILE', 'SETTINGS', 'NOTIFICATIONS', 'ACHIEVEMENTS', 'ADMIN');
CREATE TYPE usage_event_type     AS ENUM ('SECTION_VIEW', 'TRANSLATION_STARTED', 'TRANSLATION_COMPLETED',
                                          'TRANSLATION_FAILED', 'AUDIO_PLAYED', 'SIGN_VIEWED',
                                          'SEARCH_PERFORMED', 'HISTORY_ENTRY_DELETED',
                                          'PREFERENCE_CHANGED', 'NOTIFICATION_OPENED');
CREATE TYPE reference_entity     AS ENUM ('TRANSLATION', 'SIGN', 'CATEGORY', 'ACHIEVEMENT',
                                          'NOTIFICATION', 'AI_MODEL', 'USER');

-- Gamification ⏸
CREATE TYPE achievement_metric   AS ENUM ('TRANSLATIONS_COMPLETED', 'SIGNS_LEARNED',
                                          'ALPHABET_COMPLETED', 'SESSIONS_COMPLETED');

-- Cross-cutting
CREATE TYPE audit_action         AS ENUM ('INSERT', 'UPDATE', 'DELETE');
CREATE TYPE error_type           AS ENUM ('VALIDATION_ERROR', 'AUTH_ERROR', 'PERMISSION_ERROR',
                                          'NOT_FOUND', 'MODEL_INFERENCE_ERROR', 'EXTERNAL_SERVICE_ERROR',
                                          'DATABASE_ERROR', 'UNEXPECTED_ERROR');
CREATE TYPE theme_option         AS ENUM ('LIGHT', 'DARK');
```

**Three enum readings that carry design weight:**

| Enum | What it encodes |
|------|-----------------|
| `notification_channel` | **No value is audio-only, and none can be added.** `PUSH` and `IN_APP` are visual by definition, `EMAIL` is text. INV-023 is enforced here, in the type system, rather than in a guideline somebody can forget. This is the single most important line in the catalog: the users of this application are deaf and hard-of-hearing people |
| `sign_language` vs `ui_language` | Two different languages that share the English word "language". `sign_language` is the language of the *content* (LSC); `ui_language` is the language of the *interface*. They are never named alike, in the schema or in the code |
| `user_status` | Three values, not four. A temporary lockout is `locked_until`, a future timestamp that expires on its own; `BLOCKED` is the only state a human has to lift |

> ⚠️ **`output_mode` has no `BOTH`** (ALIGN-07) and **`reference_entity` declares three values nothing
> produces** (GAP-07). Both in [`open-items.md`](open-items.md).

**Changing an enum is a migration.** `ALTER TYPE … ADD VALUE` is non-transactional in PostgreSQL before
15 and cannot be rolled back inside a transaction; removing a value is not supported at all and requires
recreating the type. Adding an enum value is cheap, removing one is expensive — which is the right
incentive for a project that should not be inventing statuses casually.

## 8. Where the boundary is enforced

Each bounded context owns its tables, and **no module reads another module's tables directly.** With the
schema-per-domain layout, that boundary can be enforced rather than agreed: one database role per module,
`GRANT` only on its own schema, and a cross-module query fails at runtime instead of passing review.

Cross-domain data is reached through the owning module's repository. The one exception in this model is
`identity.users`, which almost every domain references by `user_id` — that is the Shared Kernel, and it
is shared on purpose.
